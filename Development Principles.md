Adventure Learning Development Principles
Purpose

Adventure Learning Studio will be developed incrementally.

Every feature must solve a real problem discovered while creating real learning projects.

The software serves the framework.

The framework serves the learner.

Principle 1 — Build the next thing

Never build for an imagined future.

Only build what the current project needs.

Future requirements will reveal themselves.

Principle 2 — The Driver Confidence Guide is the laboratory

The Driver Confidence Guide is not just the first project.

It is the primary source of discoveries that shape Adventure Learning.

Every improvement to the framework should first prove its value in DCG.

Principle 3 — Experience before automation

Before automating a workflow:

Perform it manually.
Understand it.
Improve it.
Then automate it.

Never automate confusion.

Principle 4 — Software follows the author

The Studio must adapt to the author's thinking.

The author should never adapt to the software.

Principle 5 — Hide complexity

Authors should think about:

learners
situations
stories
episodes
skills

Not:

folders
filenames
JSON
HTML
publishing
Principle 6 — One source, many destinations

Every learning asset should exist once.

Publishing should create:

PDF
Google Sites
Seminar slides
Mobile
Future formats

from the same source.

Principle 7 — Discover reusable concepts

Don't search for reusable code.

Search for reusable ideas.

Episodes.

Skills.

Stories.

Tony's Tips.

Situations.

Those are the real assets.

Principle 8 — Let the framework emerge

Don't invent abstractions.

Wait until three projects naturally require them.

Then create them.

Principle 9 — Measure simplicity

Every release should make one of these easier:

writing
reviewing
publishing
learning

If it doesn't, question why you're building it.

Principle 10 — Never lose sight of the learner

Every feature ultimately exists for one reason:

To help someone move from uncertainty to confidence.

If a feature doesn't contribute to that mission, it probably doesn't belong.

The Development Loop

This may become the most important diagram in the project:

Observe
      ↓
Create
      ↓
Learn
      ↓
Simplify
      ↓
Automate
      ↓
Repeat

Notice what's missing.

There's no "Design the perfect system."

The framework grows from experience.

Just as learners gain confidence through experience, the software gains maturity through experience.

Why I think this matters

A lot of projects become difficult because the software starts dictating the work.

What we've been building over the last few days says the opposite:

The Constitution protects the philosophy.
The Architecture protects the learning model.
The Studio Specification protects the author's experience.
The Domain Model protects the vocabulary.
The Development Principles protect the evolution of the software.

Those five documents form a coherent foundation. They give you a way to evaluate every future decision without getting pulled into unnecessary complexity.

And I think there's a fitting way to summarize all of them with a single sentence:

Adventure Learning is not a software project that teaches people. It is a learning philosophy expressed through software.

That feels like the vision you've been uncovering—not inventing—through the Driver Confidence Guide.
